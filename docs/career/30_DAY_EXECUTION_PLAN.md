# Thirty days: demonstrate understanding, then earn conversations

> **Owner-review draft.** Not an approved CV, profile, application or outreach message. Personal facts and contribution require owner confirmation. Vacancy observations retain their original 6 November 2026 date; recheck before use.

Start on any date; label day 1 in a private calendar. Budget **40 hours total**: four
9-hour weeks, then 2 hours each on days 29 and 30. No new large repository or platform.

**Learning allocation: 20 hours** across 20 learning days (one hour each): **12 hours
practical implementation/explanation (60%), 5 hours targeted study (25%), 3 hours
independent verification (15%)**. Each hour: 36 minutes practical, 15 study, 9 unaided
verification. The other 20 hours cover applications, outreach preparation, rehearsal and
review. If unavailable, extend the calendar rather than pretending the hours happened.

## Weekly outcomes

| Week | One primary outcome | Three important actions | Concrete deliverable | Success indicator, not a promised result |
|---|---|---|---|---|
| 1 / days 1–7 | Explain the working workflow honestly | Confirm eligibility/contribution facts; practise API/data boundary; rehearse flagship | Five-minute rehearsal + personal contribution ledger | Reproduce demo once and explain 4/5 randomly chosen workflow questions unaided |
| 2 / days 8–14 | Connect process, data and evaluation | SQL/JSON practice; analyse one real failed model case; tailor first applications | Small scratch SQL exercise + two tailored application drafts | Correctly reconcile one model failure and one cash-flow month; owner may send two eligible applications |
| 3 / days 15–21 | Start qualified conversations | Clarify threat/production boundaries; practise discovery; select matched roles/contacts | Two mock interview notes + four personalised message drafts | Two mock sessions completed; four cumulative eligible applications prepared/sent by owner |
| 4 / days 22–28 | Present and adapt without a script | Repeat unaided tasks; address feedback; rehearse employer-specific case | Captioned flagship recording and eight-application tracker | 8 tailored eligible applications and 12 owner-reviewed messages targeted; 2 substantive external conversations are an aim, not a guarantee |
| Days 29–30 | Decide next month from evidence | Review response funnel; reassess weak answers; choose one focus | One-page retrospective | Actual counts logged; one concrete adjustment chosen |

## Focused learning days — repository-linked, not a certification syllabus

Do scratch exercises locally using synthetic data, not production credentials. These are
practice tasks; **none is claimed completed**. SQL is additional learning, not a claim
the Hub currently uses a database. Prefer the existing code/tests as study sources.

| Day | Minimum topic / practical exercise | Unaided verification |
|---|---|---|
| 1 | Requirements/process: map employee → approver → decision; identify one exception | Explain the business problem in 60 seconds without 'AI transformation' jargon |
| 2 | JSON: read one API request/response; distinguish string, number, boolean, null and array | Identify three invalid inputs and expected behavior |
| 3 | REST/API: trace create, retrieve and decision endpoints in `src/Program.cs` | Explain method/path/status and why a lost response need not mean a failed write |
| 4 | Authentication/authorization: trace fixture mapping and owner/action checks | Explain why public fixture tokens are not login, and Bob's denial is not tenant isolation |
| 5 | Python fundamentals: read a function, dict/list, loop, exception and test assertion in `agent.py` | Write a tiny validation function and failing-input test without generated code |
| 8 | SQL fundamentals: create a scratch in-memory SQLite table for five synthetic requests | SELECT/filter/group pending requests; predict results before running |
| 9 | SQL/data thinking: add a synthetic decision table; join requests to decisions | Explain missing decisions and avoid counting pending requests as completed |
| 10 | Git/CI: inspect source commit, test workflow and actual run | Explain branch vs commit vs PR; demonstrate why old main green is not new-branch green |
| 11 | Testing/reliability: run retry/conflict test and read `Commit` | Predict what survives failed write and restart, then check |
| 12 | Business case: hand-calculate one monthly ramp output and compare scenarios | Explain negative year-one value and capacity versus cash |
| 15 | LLM fundamentals: context, tokens, probabilistic output and structured schema | Explain why JSON schema cannot guarantee a relevant answer |
| 16 | Agent/tool boundary: deterministic reference versus optional model selector | Show that model output cannot invoke approval; identify separate confirmed submission |
| 17 | RAG fundamentals: source filtering, retrieval, context and citations | Explain this corpus fits context; do not claim vector/hybrid search |
| 18 | Evaluations: classify one failed holdout case against raw report | Separate model calls, pre-model safeguards, relevance, abstention and overall totals |
| 19 | Governance: threat model, human ownership, escalation and evidence retention | Explain why an allowed source can be wrong without leaking filtered data |
| 22 | Cloud fundamentals: identity, secret, compute, storage, logs and service costs | Sketch proposed cloud responsibilities; label every unimplemented component |
| 23 | Process/adoption: proposed pilot owners, support, training, acceptance | Role-play Finance disagreement; record it as a proposed exercise, not a real workshop |
| 24 | Product thinking: problem, alternative, success metric, countermetric and stop gate | Explain why 'more model answers' can worsen usefulness |
| 25 | Debugging: reproduce a safe test failure and inspect response/log | Explain cause and repair without pasting an AI explanation |
| 26 | Independent synthesis: run the five-minute case and answer a surprise question | 8/10 across five randomly chosen interview questions, repeated later |

Targeted study uses the matching source/test/architecture guide first. Check current
official documentation when you need actual library/API syntax. Avoid buying courses or
studying every AI framework. During the unaided nine minutes: close AI/chat and notes,
write/predict/explain first, then compare with source/test output and record corrections.

## Career-action days and private tracking

Days 6–7: confirm actual qualifications, language/mobility/start-date facts; select two
eligible roles and record a rehearsal. Days 13–14: tailor first two applications and
three message drafts; owner sends only after review. Days 20–21: perform two mock
interviews, prepare two more eligible applications and four additional messages.
Days 27–28: adapt from feedback, prepare four further applications and five further
messages, and caption the demonstration. Each of these days has a two-hour action block.
Days 29–30 each use two hours for follow-up/review, not starting another build.

Track: hard eligibility, specific portfolio relevance, date/URL, preparation, owner
submission, response, conversation, next step. Use actual counts; draft is not sent,
reply is not interview, interview is not offer. If eight eligible roles cannot be found,
record fewer and improve fit rather than inventing openings or mass-applying.

At day 30 choose one adjustment: improve evidence explanation, broaden honest search
titles/location, or address one repeated technical gap. Do not respond to silence by
building another large repository or claiming seniority.
